# 非機能要件

## この文書について

「何ができるか」（機能）は [要件定義書](requirements.md) に書きました。この文書には、「**どのくらいの品質で動くか**」（非機能要件）をまとめます。速さ、止まりにくさ、安全さなどです。

各項目に、2種類の値を並べています。

| 列 | 意味 |
|---|---|
| **顧客に約束する値** | お客さんに「最低限これは守ります」と約束する値。守れないと契約違反になるので、確実に守れる値にする |
| **技術者として目指す値** | 開発チームが内部で目指す値。約束の値より厳しくしておき、余裕を持って約束を守れるようにする |
| **確認方法** | その値を守れているかを、どうやって確かめるか |

あとで、顧客向けと技術者向けの文書に分ける予定です。

項目の分け方は、IPA（情報処理推進機構）の「非機能要求グレード」を参考にしています。

> 本番環境は AWS（ECS Express Mode と RDS。東京リージョン）です（[infra/README.md](../infra/README.md)）。各項目を確かめた結果は、最後の「確認の結果」にまとめています。

## 1. 性能（速さ）

| 項目 | 顧客に約束する値 | 技術者として目指す値 | 確認方法 |
|---|---|---|---|
| 画面の表示時間 | 3秒以内に表示される | 主な内容が 2.5秒以内に表示される（Google が「良好」とする基準） | ブラウザの開発者ツール（Lighthouse）で測る |
| API の応答時間 | ― （画面の表示時間で約束する） | 95% のリクエストが 0.5秒以内に返る | 負荷テストのツールで測る |
| 同時に使える人数 | 100人が同時に使っても、上の時間を守る | 申込みが1秒間に50件来ても、上の時間を守る | 負荷テストのツールで測る |
| 扱えるデータの量 | ユーザー 1万人、コミュニティ 1,000件、イベント 1万件で、上の時間を守る | 同じ件数のテスト用データを入れて測る。一覧は必ずページに分けて取得する | テスト用データを入れて測る |
| イベントの検索 | 検索結果が 3秒以内に表示される | イベント 1万件のうち開催前のものから探して、95% の検索が 0.5秒以内に返る。遅い場合は、PostgreSQL の部分一致用の索引（pg_trgm）を使う | テスト用データを入れて測る |
| 画面のファイルの大きさ | ― | 最初に読み込む JavaScript が 200KB 以下（圧縮後） | `npm run build` の結果で確認する |

## 2. データの正しさ

このアプリで一番大事な項目です。

| 項目 | 顧客に約束する値 | 技術者として目指す値 | 確認方法 |
|---|---|---|---|
| 定員を超えない | 定員を超えて申込みが入ることはない | 残り1枠に 100件の申込みが同時に来ても、超過は 0件 | 同時に申込みを送る自動テストで確かめる |
| 二重に申し込まれない | 同じ人が同じイベントに2回申し込めない | 画面のボタンの連打や、同時のリクエストでも重複 0件。データベースの制約（ユニーク制約）でも防ぐ | 自動テストで確かめる |
| 操作の途中で失敗したとき | データが中途半端な状態で残らない | 複数の更新をまとめて成功・失敗させる（トランザクション） | 自動テストで、途中でエラーを起こして確かめる |

## 3. セキュリティ（安全さ）

| 項目 | 顧客に約束する値 | 技術者として目指す値 | 確認方法 |
|---|---|---|---|
| 通信の暗号化 | すべての通信を暗号化する（HTTPS） | HTTP で来たアクセスは HTTPS に移動させる | ブラウザで確認する |
| パスワードの保存 | パスワードをそのまま保存しない | BCrypt という方式で変換して保存する | データベースの中身を確認する |
| パスワードの条件 | 8文字以上 | 8文字以上。長いパスワード（64文字まで）も使えるようにする | 自動テストで確かめる |
| ログインの試行制限 | 何度も間違えるとログインできなくなる | 5回続けて失敗したら、15分間ロックする | 自動テストで確かめる |
| ログインの有効期限 | 一定時間操作がないとログアウトされる | 30分間操作がなければログアウト | 自動テストで確かめる |
| パスワードを変えたとき | パスワードを変えたら、ほかの端末のログインは使えなくなる | 変えた日時より前に作られたセッションを、次の API の呼び出しで止める。変えた端末は、セッションを作り直してログインしたままにする（要件定義書 5.13） | 自動テストと E2E テストで確かめる |
| パスワードの再設定 | 登録しているメールアドレスかどうかを、他人に知られない。再設定のリンクは短い時間だけ、1回だけ使える | 返事はいつも同じ。トークンは 256ビットの乱数で、SHA-256 の値だけを保存する。30分で期限切れ。同じ IP アドレスからの依頼は1時間に5回まで。メールを送る仕組みができるまで、本番では止める | 自動テストで確かめる |
| 権限のない操作 | 権限のない人は、他人のコミュニティを編集できない | すべての API で、バックエンドが権限をチェックする。画面のボタンを隠すだけにしない | 権限のない人で API を呼ぶ自動テストで確かめる |
| よくある攻撃への対策 | 一般的な攻撃への対策を行う | OWASP Top 10（代表的な攻撃10種の一覧）に対策する。特に SQL インジェクション、XSS、CSRF | 自動テストとコードレビューで確かめる |
| 検索の入力の扱い | 検索に何を入力しても、ほかの人の情報が見えたり、アプリが止まったりしない | 入力した単語を SQL に直接つなげない（MyBatis の `#{}` を使う）。`%` と `_` はただの文字として扱う。100文字、5語を超える入力は切り捨てる | 記号や長い文字列を入力する自動テストで確かめる |
| Cookie の設定 | ― | ログイン用の Cookie に HttpOnly、Secure、SameSite を付ける | ブラウザの開発者ツールで確認する |
| 外部パッケージの脆弱性 | 既知の重大な脆弱性を放置しない | 深刻度が「高」以上の脆弱性は 0件 | `npm audit`、GitHub の Dependabot で確認する |
| 個人情報の扱い | 個人情報は目的以外に使わない | ログにパスワードやメールアドレスを出力しない | コードレビューで確認する |

## 3.1 個人情報の保護

| 項目 | 顧客に約束する値 | 技術者として目指す値 | 確認方法 |
|---|---|---|---|
| アカウント削除後の個人情報 | 削除の操作をした時点で、ニックネームはほかの人から見えなくなる。30日以内にバックアップも含めて、本名、ニックネーム、メールアドレスが完全に消える | 削除の操作と同時に、データベースの本名、ニックネーム、メールアドレスを消す。バックアップの保存期間を 30日以内にして、古いバックアップが自動で消えるようにする | 自動テストで、削除後に元の値が残っていないことを確かめる |
| 他人に見せる個人情報 | ほかのユーザーに見せるのはニックネームだけ。オーナーと運営スタッフにも、本名とメールアドレスは見せない | 本名とメールアドレスは、本人と管理者以外には API で返さない。画面で隠すだけにしない。API が返す項目を必要最小限にする | 自動テストで、本人以外に対して API が本名とメールアドレスを返さないことを確かめる |

## 4. 可用性（止まりにくさ）

本番環境を決めたときに見直します。

| 項目 | 顧客に約束する値 | 技術者として目指す値 | 確認方法 |
|---|---|---|---|
| 稼働率 | 99%（1か月に約7時間までの停止） | 99.5%（1か月に約3.6時間までの停止） | 外部の監視サービスで、定期的にアクセスして確かめる |
| 計画的な停止 | 3日前までにお知らせする | 更新作業は、利用の少ない夜間に行う | ― |
| 故障からの復旧 | 翌営業日までに復旧する | 4時間以内に復旧する | 復旧の手順書を作り、実際に試す |
| データのバックアップ | 1日1回バックアップを取る | 1日1回に加え、直前の状態まで戻せる仕組みを使う | バックアップから戻す手順を、実際に試す |

## 5. 運用・保守（直しやすさ、調べやすさ）

| 項目 | 顧客に約束する値 | 技術者として目指す値 | 確認方法 |

| 障害の連絡 | 障害が起きたら、お知らせする | エラーが増えたら、開発者に自動で通知が届く | わざとエラーを起こして確かめる |
| ログ | ― | 1つの操作のログを追えるように、リクエストごとに ID を付ける。ログは 30日間残す | ログを確認する |
| 自動テスト | ― | 業務処理（Service）のテストで、コードの 80% 以上を通る | テストの網羅率を測るツール（JaCoCo）で確認する |
| 自動チェック | ― | PR を作ると、ビルド、テスト、lint が自動で実行される | GitHub Actions で確認する |
| テーブルの変更 | ― | テーブルの変更は、すべて Flyway の履歴に残す | コードレビューで確認する |
