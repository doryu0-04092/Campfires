# API 仕様書

画面（React）とバックエンド（Spring Boot）の間でやり取りする API の仕様です。画面も、偽の API（MSW）も、本物の API も、この仕様書のとおりに作ります。

| ファイル | 内容 |
|---|---|
| `README.md`（このファイル） | API 全体の共通ルールと、仕様書の読み方 |
| [`openapi.yaml`](openapi.yaml) | 仕様書の本体。OpenAPI という世界標準の形式で書いている |

仕様を変えるときは、先にこの仕様書を直してから、コードを直します（[技術構成](../tech-stack.md) 5章）。

## 1. 共通ルール

### 1.1 URL

| ルール | 例 |
|---|---|
| すべての API は `/api` で始める | `/api/events` |
| ものの名前は**複数形の英語**にする | `/api/communities`（community ではなく communities） |
| 1件を指すときは、名前の後ろに番号を付ける | `/api/communities/3`（3番のコミュニティ） |
| 親子の関係は、URL の階層で表す | `/api/communities/3/events`（3番のコミュニティのイベント） |
| 単語が2つ以上のときは、`-`（ハイフン）でつなぐ | `/api/join-requests` |

**画面の URL との違い**：画面の URL（`/communities/3` など）は、ブラウザのアドレスバーに表示されるもので、`docs/screens.md` で決めています。API の URL は、画面の裏で画面がデータを取りに行く先で、必ず `/api` で始まります。似ていますが、別物です。

### 1.2 操作の種類（HTTP メソッド）

同じ URL でも、**操作の種類**によって、することが変わります。

| メソッド | 読み | すること | 例 |
|---|---|---|---|
| `GET` | ゲット | 取得する（データは変えない） | `GET /api/communities/3`：3番のコミュニティを取得する |
| `POST` | ポスト | 新しく作る | `POST /api/communities`：コミュニティを作る |
| `PATCH` | パッチ | 一部を変える | `PATCH /api/communities/3`：3番のコミュニティの名前などを変える |
| `DELETE` | デリート | 消す | `DELETE /api/communities/3`：3番のコミュニティを消す |

「申し込む」「承認する」のような、作る・変える・消すに当てはめにくい操作も、なるべく「何かを作る・消す」と考えて表します。例：「イベントに申し込む」は「申込みを作る」（`POST /api/events/5/applications`）。

### 1.3 データの形式

| 項目 | ルール | 例 |
|---|---|---|
| 形式 | JSON（ジェイソン）。`{ "名前": 値 }` の形で書く、データのやり取りの標準的な形式 | `{ "title": "Java 勉強会" }` |
| 項目の名前 | 英語の**キャメルケース**（2つ目以降の単語の先頭を大文字にする） | `communityName`、`startAt` |
| 番号（ID） | 整数 | `3` |
| 日時 | **世界標準時の ISO 8601 形式**。末尾の `Z` が世界標準時の印。日本時間への変換は画面で行う | `"2026-10-10T10:00:00Z"`（日本時間の 19:00） |
| ない値 | `null` | `"description": null` |

### 1.4 返事の状態（HTTP ステータスコード）

API の返事には、結果を表す3桁の番号が付きます。

| 番号 | 意味 | このアプリで使う場面 |
|---|---|---|
| `200` | 成功 | 取得・変更が成功した |
| `201` | 作成した | 作成が成功した（返事に、作ったものを入れる） |
| `204` | 成功（返す中身なし） | 削除・ログアウトが成功した |
| `400` | 入力が正しくない | 必須の項目がない、文字数が多すぎる など |
| `401` | ログインしていない | ログインが必要な API を、ログインせずに呼んだ |
| `403` | 権限がない | オーナー以外がコミュニティを編集しようとした など |
| `404` | 見つからない | 存在しないコミュニティやイベントを指定した |
| `409` | 今の状態ではできない | 満席、同じイベントに二重に申し込んだ、締め切りを過ぎた など |
| `202` | 受け付けた | パスワードの再設定の依頼を受け付けた（登録されていても、いなくても同じ返事） |
| `429` | 試しすぎ | ログインを続けて失敗し、ロックされた。同じ IP アドレスから、ログイン・登録・再設定の依頼をしすぎた |
| `500` | サーバーの中でエラーが起きた | 想定していないエラー |
| `503` | 今は使えない | パスワードの再設定を止めている（メールを送る仕組みがないため。`PASSWORD_RESET_UNAVAILABLE`） |

**200番台は成功、400番台は呼び出した側（画面や利用者）の問題、500番台はサーバー側の問題**、と覚えておくと便利です。

### 1.5 エラーの返し方

エラーのときは、すべての API で同じ形の返事を返します。**RFC 9457（Problem Details）**という、エラーの返し方の世界標準の形式に合わせています。Spring Boot がこの形式に対応しているためです。

```json
{
  "type": "about:blank",
  "title": "Conflict",
  "status": 409,
  "detail": "このイベントは満席です。",
  "code": "EVENT_FULL"
}
```

| 項目 | 意味 |
|---|---|
| `status` | HTTP ステータスコード（上の表の番号） |
| `title` | ステータスコードの短い説明（英語） |
| `detail` | 利用者に見せてよい、日本語の説明 |
| `code` | エラーの種類を表す、決まった英語の記号。**画面はこれを見て、表示を変える**（`detail` の文章は変わることがあるため、文章で判断しない） |
| `errors` | 入力のチェックで引っかかった項目の一覧（400 のときだけ） |

入力のチェックで引っかかったとき（400）は、どの項目が、なぜだめだったかを `errors` に入れます。

```json
{
  "type": "about:blank",
  "title": "Bad Request",
  "status": 400,
  "detail": "入力内容に誤りがあります。",
  "code": "VALIDATION_ERROR",
  "errors": [
    { "field": "title", "message": "タイトルを入力してください。" },
    { "field": "capacity", "message": "定員は1以上にしてください。" }
  ]
}
```

**エラーの文に、内部の情報を入れない**：プログラムの内部の情報（SQL の文、ファイルの場所など）は、攻撃の手がかりになるので、`detail` に入れません（[非機能要件](../non-functional-requirements.md) 3章、OWASP Top 10 の A02）。

### 1.6 ログイン（認証）

| 項目 | ルール |
|---|---|
| 方式 | セッション方式。ログインに成功すると、サーバーがログインの証明（セッション ID）を Cookie で渡す |
| Cookie の設定 | `HttpOnly`、`Secure`、`SameSite=Lax` を付ける（[非機能要件](../non-functional-requirements.md) 3章） |
| 画面側の扱い | 画面のプログラムは、セッション ID に触れない。ブラウザが自動で Cookie を送る |
| 有効期限 | 30分間操作がなければ、ログアウトになる |
| ログインが必要な API | 仕様書の各 API に「ログインが必要」と書く。ログインせずに呼ぶと 401 |
| パスワードを変えたとき | 変えた日時より前に作られたセッション（ほかの端末のログイン）は、次の呼び出しで 401 になる。変えた端末には、新しいセッション ID を渡す（パスワードの変更・再設定。[要件定義書](../requirements.md) 5.13） |

### 1.7 CSRF の対策

データを変える API（`POST`、`PATCH`、`DELETE`）では、**CSRF トークン**という合言葉を一緒に送ってもらいます。罠のサイトから勝手に操作を送らせる攻撃（CSRF）を防ぐためです。

1. サーバーは、`XSRF-TOKEN` という名前の Cookie に、合言葉を入れて渡す
2. 画面は、データを変える API を呼ぶとき、その合言葉を `X-XSRF-TOKEN` というヘッダー（通信に付ける追加の情報）に入れて送る
3. サーバーは、Cookie とヘッダーの合言葉が一致するかを確かめる。一致しなければ 403

罠のサイトは、Campfires の Cookie の中身を読めないので、正しい合言葉をヘッダーに入れられません。これは Spring Security が用意している仕組みで、SameSite と合わせて二重に防ぎます（多層防御）。

### 1.8 一覧とページ

一覧を返す API は、すべて同じ形にします。

| 項目 | ルール |
|---|---|
| ページの指定 | `?page=2` のように、URL にページ番号を付ける。1から始まる。付けなければ1ページ目 |
| 1ページの件数 | 30件 |
| 返事の形 | `items`（そのページのデータ）、`totalCount`（全部の件数）、`page`、`pageSize`、`totalPages` |

### 1.9 個人情報

| 項目 | ルール |
|---|---|
| ほかのユーザーに返す名前 | ニックネームだけ |
| 本名とメールアドレス | 本人の情報を返す API（アカウント設定）でだけ返す。**ほかの API では、項目そのものを返さない**（画面で隠すだけにしない） |
| アカウントを削除した人 | ニックネームの代わりに `null` を返し、画面で「退会したユーザー」と表示する |

（[要件定義書](../requirements.md) 5.6、[非機能要件](../non-functional-requirements.md) 3.1）

### 1.10 バージョン

MVP の間は、URL にバージョン（`/api/v1/` など）を付けません。画面とバックエンドを同時に更新するため、古い画面のために古い API を残しておく必要がないからです。

## 2. 仕様書（openapi.yaml）の読み方

### 2.1 OpenAPI とは

API の仕様を書くための**世界標準の形式**です。決まった書き方で書くので、人によって書き方がばらばらにならず、専用のツールで見やすく表示したり、ほかのツールで読み込んだりできます。Spring Boot からも扱えます。

### 2.2 YAML の書き方

`openapi.yaml` は **YAML**（ヤムル）という書式で書いています。

| 書き方 | 意味 | 例 |
|---|---|---|
| `名前: 値` | 項目と値の組 | `title: Campfires API` |
| 字下げ（空白2つ） | 字下げした行は、上の行の中身 | 下の例を参照 |
| `- ` | 一覧の1つ | `- name: events` |
| `#` | その行の終わりまでコメント | `# ここはコメント` |

```yaml
info:                      # info の中身は、字下げした下の2行
  title: Campfires API
  version: 0.1.0
```

**字下げの空白の数がずれると、意味が変わる**ので注意が必要です。タブは使えず、空白だけを使います。

### 2.3 全体の構成

```yaml
openapi: 3.1.0       # OpenAPI のどのバージョンの書き方か
info: ...            # この API の名前と説明
servers: ...         # API の置き場所
tags: ...            # API のまとまり（アカウント、コミュニティ、イベントなど）
paths: ...           # ★ API の一覧。ここが本体
components: ...      # 何度も使う部品（データの形、エラーの返事など）
```

### 2.4 1つの API の読み方

`paths` の中の1つの API は、次のように書きます（例）。

```yaml
paths:
  /api/communities/{communityId}:     # ① URL。{ } の部分には番号が入る
    get:                              # ② 操作の種類（GET＝取得）
      summary: コミュニティの詳細を取得する   # ③ 一言の説明
      tags: [communities]             # ④ どのまとまりか
      parameters:                     # ⑤ URL に入れる値
        - $ref: '#/components/parameters/CommunityId'
      responses:                      # ⑥ 返事の一覧（ステータスコードごと）
        '200':                        #    成功したとき
          description: 成功
          content:
            application/json:
              schema:
                $ref: '#/components/schemas/CommunityDetail'   # ⑦ 返すデータの形
        '404':                        #    見つからないとき
          $ref: '#/components/responses/NotFound'
```

| 番号 | 読むところ | 分かること |
|---|---|---|
| ① | URL | どこを呼ぶか |
| ② | `get` / `post` / `patch` / `delete` | 何をするか |
| ⑤ | `parameters` | URL に何を入れるか |
| （なし） | `requestBody` | 送るデータの形（作成・変更のとき） |
| ⑥ | `responses` | 結果ごとに、何が返ってくるか |
| ⑦ | `schema` | 返ってくるデータの形 |

### 2.5 `$ref` とは

`$ref`（レフ、reference＝参照の略）は、「**この部分は、別の場所に書いてあるものを使う**」という意味です。

```yaml
$ref: '#/components/schemas/CommunityDetail'
```

これは「`components` の中の `schemas` の中の `CommunityDetail` を見てください」という意味です。同じデータの形やエラーの返事を何度も書かずに済み、直すときも1か所で済みます。TypeScript の `import` と似た考え方です。

エディタによっては、`$ref` の上で `Ctrl` + クリックすると、参照先に飛べます。

### 2.6 見やすく表示する方法

`openapi.yaml` はそのままでも読めますが、専用のツールを使うと、API ごとに整理された画面で見られます。

| 方法 | 内容 |
|---|---|
| VS Code・Cursor の拡張機能 | 「OpenAPI」で検索すると、仕様書を見やすく表示する拡張機能がある。書き間違いも教えてくれる |
| Swagger Editor（スワッガー エディター） | ブラウザで使える公式のツール。`openapi.yaml` の中身を貼り付けると、左に本文、右に見やすい画面が出る |

どちらも必須ではありません。使う場合は、信頼できる提供元のものを選んでください。

### 2.7 コメントのルール

`openapi.yaml` も、ほかのコードと同じく日本語で説明を付けます。

- 各 API と各データの形に、`summary`（一言の説明）と `description`（詳しい説明）を日本語で書く。**この説明はツールの画面にも表示される**
- ツールの画面に出す必要のない、書き方の補足は `#` のコメントで書く
